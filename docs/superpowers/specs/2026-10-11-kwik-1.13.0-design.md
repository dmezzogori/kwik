# kwik 1.13.0 — design

Date: 2026-10-11. Status: approved design forks, spec under review.

## Purpose

One MINOR release carrying five fixes that teban needs from its framework. Each item is proven against kwik's
own suite and against teban's backend suite (run in a teban worktree through an uncommitted editable overlay)
before release. After 1.13.0 is on PyPI, teban bumps its pin and removes the workarounds kwik now covers.

Source issues (kheperer-labs/teban): #823, #757, #777, #908 (kwik part), #378 / #302 (kwik route items and the
password policy).

## Success criteria

- Every route's writes are committed before the response is sent (#823).
- On a gunicorn restart, open streaming responses are cancelled before gunicorn kills the worker, so their
  cleanup code runs (#757).
- Pool size, overflow and checkout timeout are explicit settings with documented reasoning; a starved checkout
  fails in `POSTGRES_POOL_TIMEOUT` seconds, not 30 (#777).
- An inactive role grants nothing and is not reported as held by any kwik role or permission read (#908).
- Apps have a supported, fail-loud way to exclude kwik's built-in routes so they can override or withdraw them;
  every new password meets a configurable minimum length (#378 / #302).
- `uv run pytest` and `uv run ruff check` / `ruff format --check` are green in kwik; teban's `uv run pytest` is
  green against the local kwik.

## Item 1 — commit before the response is sent (#823)

**Problem.** `kwik.dependencies.session._get_session` commits in its `yield` teardown. In FastAPI 0.140 a
request-scoped yield dependency exits after the response has been sent, so a client acting on the response at
once can read the database before the write is committed.

**FastAPI facts this relies on (0.140.7, `fastapi/routing.py`, `fastapi/dependencies/utils.py`).**
- The route handler runs inside two exit stacks: `function_stack` closes after the handler returns — after the
  endpoint ran and the response was serialized — and before `await response(...)`; `request_stack` closes after
  the response was sent.
- `Depends(..., scope="function")` puts a yield dependency on `function_stack`.
- A request-scoped yield dependency may not depend on a function-scoped one (`DependencyScopeError`). The
  reverse is allowed.
- Within one request, a dependency is cached by callable, so two dependants of `_get_session` get the same
  session object. `dependency_overrides` applies to sub-dependencies.

**Design.** Keep `_get_session` request-scoped and unchanged in behaviour (it still owns the session, commits
anything left over and closes it after the response). Add `_commit_session`, a yield dependency that depends on
`_get_session` and commits after the handler returns:

```python
def _commit_session(session: Annotated[_Session, Depends(_get_session)]) -> Generator[None, None, None]:
    yield
    session.commit()
```

`Kwik._init_fastapi_app` installs it app-wide: `FastAPI(..., dependencies=[Depends(_commit_session,
scope="function")])`. App-level dependencies are added to every route included afterwards, HTTP and WebSocket.

**Behaviour.**
- Success: the commit happens after serialization and before the status line is sent. Lazy loads during
  serialization still work (the session is open).
- The endpoint raises: the exception passes through `_commit_session` without committing; `_get_session`'s
  `session_scope` rolls back as today.
- The commit itself fails: the exception propagates before any byte is sent, `session_scope` rolls back, and the
  client gets a 5xx instead of today's false 2xx.
- Streaming bodies and background tasks run after `function_stack` closed. The session is still open; any
  writes they make are committed by `_get_session`'s teardown, as today.
- Routes that never touch the database get a `Session` object but no connection (SQLAlchemy checks one out on
  first use).
- `Session` (the `Annotated` alias) is unchanged, so request-scoped yield dependencies on it stay legal.

**Tests (kwik).** A route that inserts a row, behind an ASGI wrapper that, on `http.response.start`, reads the
row through a separate connection: the row must be visible. A route that raises after writing: the row is
absent. A route that streams after writing: the row is committed by the end. A dependency override of
`_get_session` is honoured by `_commit_session`.

**teban follow-up.** Its test `session` fixture (PR #819, SAVEPOINT restart on the fixture's own savepoint
only) sees the same `commit()` calls as before, just earlier: teban's suite must stay green unchanged. Then
remove the explicit `context.session.commit()` calls in `api/portal/auth.py` (`consume`, `logout`) if teban's
suite, including the #806 regression tests, stays green without them.

## Item 2 — graceful shutdown below gunicorn's timeout (#757)

**Problem.** `run()` sets no gunicorn `graceful_timeout` (default 30 s) and `KwikUvicornWorker` sets no
`timeout_graceful_shutdown`, so uvicorn waits on open streams until gunicorn SIGKILLs the worker and their
shielded cleanup never runs.

**Design.**
- New setting `BACKEND_GRACEFUL_TIMEOUT: int = 30` (seconds, ≥ 1). `run()` passes it to gunicorn as
  `graceful_timeout`.
- `KwikUvicornWorker.__init__` calls the parent, then sets
  `self.config.timeout_graceful_shutdown = max(self.cfg.graceful_timeout - GRACEFUL_SHUTDOWN_MARGIN, 1)` with
  `GRACEFUL_SHUTDOWN_MARGIN = 5` seconds. Deriving it from the gunicorn value keeps the two from drifting apart,
  whatever value the app configures; the margin leaves time for cancelled tasks' cleanup and the lifespan
  shutdown before the SIGKILL.

**Tests (kwik).** The worker built with a gunicorn config whose `graceful_timeout` is 30 has
`timeout_graceful_shutdown == 25`; with 3 it is 1. `run()` in production mode passes
`graceful_timeout=settings.BACKEND_GRACEFUL_TIMEOUT` to gunicorn.

**teban follow-up.** None in code. #757's Redis-lease acceptance check is a post-deploy observation recorded on
the PR's QA note.

## Item 3 — explicit pool sizing and checkout timeout (#777)

**Problem.** `create_engine` hardcodes `pool_size=10`, `max_overflow=20` and leaves `pool_timeout` at
SQLAlchemy's 30 s. A request that finds the pool exhausted holds its thread for 30 s and then fails.

**Design.**
- New settings: `POSTGRES_POOL_SIZE: int = 10`, `POSTGRES_MAX_OVERFLOW: int = 20`,
  `POSTGRES_POOL_TIMEOUT: float = 10.0` (seconds, > 0). `create_engine` passes them through.
- Default timeout 10 s: shorter than teban's 15 s lease-renewal interval, so a starved renewal fails before the
  next one is due, and far shorter than a proxy's request timeout, so the client sees a specific error rather
  than a gateway timeout. Pool size and overflow keep today's values, so only the timeout changes behaviour.
- Each worker process has its own pool. The lifespan logs a warning when
  `BACKEND_WORKERS * (POSTGRES_POOL_SIZE + POSTGRES_MAX_OVERFLOW) > POSTGRES_MAX_CONNECTIONS` (an existing
  setting), naming the three numbers.
- The handbook gets a "Database connection pool" section with this reasoning and the sizing rule.

**Tests (kwik).** The engine's pool reports the configured size, overflow and timeout. With size 1, overflow 0
and timeout 0.2, a second checkout raises `sqlalchemy.exc.TimeoutError` in well under a second. The warning is
logged when the product exceeds the connection limit and not otherwise.

**teban follow-up.** #777's second acceptance item: confirm the notification stream ends with a logged,
specific reason when a renewal hits the pool timeout, adding the log line if it is missing.

## Item 4 — inactive roles are held by no one (#908)

**Owner decision (#908).** A deactivated role is held by no one.

**Design.** `User.roles` stays the raw assignment list: admin screens need to show and remove an inactive role
that is still assigned, and `users_roles` rows are untouched by deactivation. Every read that answers "what does
this user hold" counts active roles only:
- `crud_users.has_permissions`: the aggregate query joins `roles` and requires `Role.is_active`; the detached
  fallback filters too.
- `crud_users.has_roles`, `get_roles`, `get_permissions`: active roles only.
- `User.permissions` (hybrid property): permissions of active roles only.
- `GET /users/me/roles` and `GET /users/me/permissions` follow, since they call `get_roles` / `get_permissions`.

Role-management reads (`crud_roles.get_users_with`, `Role.users`, `GET /roles/{id}/users`) keep listing
assignments, active or not.

**Tests (kwik).** A user whose only role holding a permission is inactive fails `has_permissions` (attached and
detached), `has_roles`, and the `has_permission` dependency on a route (403); `get_roles`, `get_permissions`,
`/users/me/roles` and `/users/me/permissions` omit the role and its permissions; reactivating restores them.

**teban follow-up.** Remove `teban/core/active_roles.py` (the `_ActiveRoleCRUDUsers` class swap) and its
install call and test, and the `/users/me/roles` and `/users/me/permissions` re-declarations in
`user_overrides_router` if they now return the same as kwik's. Keep teban's own admin-membership and
time-visibility filters, which are teban code.

## Item 5 — built-in route exclusion and password policy (#378 / #302)

### 5a. `kwik.api.build_api_router(exclude=...)`

**Problem.** Apps cannot restrict kwik's built-in routes (`PUT /users/{id}/reset-password`,
`DELETE /roles/{id}/users`, role updates). Registering an override first wins dispatch, but leaves a duplicate
operation whose unguarded handler is the one OpenAPI documents. teban works around it by copying and filtering
kwik's routers (`teban.api_router._filtered`).

**Design.** `build_api_router(*, exclude: Iterable[tuple[str, str]] = ()) -> APIRouter` returns a new router
carrying the routes of `login_router`, `users_router`, `roles_router` and `permissions_router`, minus every
excluded `(METHOD, path)` pair. Paths are full paths as served under the API prefix (`"/roles/{role_id}/users"`),
methods are upper-case. It raises `ValueError` when:
- an excluded pair matches no route (a kwik upgrade renamed or moved it: fail at import, not silently restore);
- a pair matches a route that serves other methods too (dropping the route would withdraw them).

Route objects are moved as they are, so response models, dependencies and OpenAPI metadata of the routes that
stay are untouched. `kwik.api.api_router` becomes `build_api_router()`: same routes, same order. Apps register
their own overrides before including the result. The canonical-role rules (role renames, the last
administrator) stay app code: kwik has no notion of canonical roles.

**Tests (kwik).** No exclusion reproduces today's route set. Excluding a pair drops exactly that route and the
OpenAPI document has one operation for an overridden pair. An unknown pair and a partial-method match raise.

### 5b. Password policy

**Design.** New setting `PASSWORD_MIN_LENGTH: int = 12` (1 ≤ value; minimum length in characters). No
composition rules, following NIST SP 800-63B. `NewPassword`, which already enforces bcrypt's 72-byte bound,
also enforces the minimum length, so the policy covers every schema built on it: `UserRegistration.password`,
`UserPasswordChange.new_password`, `AdminPasswordReset.new_password`, and app schemas that reuse `NewPassword`.
`POST /login/reset-password` takes its `password` body field as `NewPassword` (today a bare `str`).

- The minimum is process-wide: `kwik.security.configure_password_policy(min_length=...)`, called by `Kwik` from
  settings at construction. Without a call (scripts, Celery workers) the default is the setting's default, 12.
- Seeds and scripts that create accounts from configuration (the first superuser, test fixtures) bypass the
  minimum by validating with `context={"password_policy": False}`
  (`UserRegistration.model_validate({...}, context=...)`). The bcrypt bound still applies. kwik's own testing
  fixtures use this, so `FIRST_SUPERUSER_PASSWORD="admin"` keeps working in development.
- Verifying a password (login, `old_password`) stays unconstrained: existing accounts with shorter passwords
  can still sign in and change their password.
- Violations are a 422 from request validation, with a message naming the minimum.

**Tests (kwik).** Each of the four endpoints rejects an 11-character password with 422 and accepts a
12-character one; the bypass context accepts a short one and still rejects one over 72 bytes; a configured
minimum of 16 is honoured; login with a pre-existing short password still works.

**teban follow-up (5a + 5b).** Replace `_filtered` and its two exclusion maps with
`build_api_router(exclude=...)` (keeping the comments on why each route is overridden or withdrawn); make
`init_superuser` and any config-driven account seed validate with the bypass context; use `NewPassword` in
teban's own password-reset schema if it does not already. Comment on #378 and #302: what teban already did on
main (F2 and F23 via overrides and withdrawal, F30 via canonical-role protection) and what kwik 1.13.0 takes
over (the exclusion mechanism, the password policy item of #302).

## Breaking changes (called out in the CHANGELOG)

- New passwords shorter than 12 characters are rejected (configurable).
- A starved pool checkout fails after 10 s instead of 30 s (configurable).
- Inactive roles grant no permissions and are not returned by `get_roles` / `/users/me/roles`.
- A commit failure now yields a 5xx instead of a 2xx sent before the failure.
